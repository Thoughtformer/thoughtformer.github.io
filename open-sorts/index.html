OpenSorts is my exploration of making open-source software more approachable to people who have ideas but don't necessarily know how to find, evaluate, or adapt code. The longer-term ambition is to help someone start with an idea, discover useful foundations, and shape a result through ordinary language.

Why this interests me

Good tools should not be hidden behind unnecessary barriers.

There is an enormous amount of useful, creative work in open-source projects. For someone without development experience, the difficulty often begins before they can even decide whether a project is right for them.

I want to explore an experience that begins with what someone wants to accomplish, not with a command line or repository browser. It should help people understand possible starting points while being transparent about source licenses, compatibility, and what has actually been verified.

The larger concept has three entrances: describe an idea, browse projects that catch your attention, or select several foundations and explore what they could become together. Combining unrelated software is not assumed to work automatically.

What exists today

Discovery first, creation later.

The in-development workspace has moved beyond an idea on paper. Its current branch includes a browser interface and live read-only project discovery. Recent pull-request notes document type checking, 24 passing tests, a production build, and local browser checks. These are development checks, not proof of a production service.

Explore real projects

Search public GitHub and GitLab repositories, browse outcome-based categories, and refine loaded results by available metadata. Source links remain available.

Keep promising foundations

Bookmark projects, select multiple starting points, save ideas and conversation notes in the browser, and export workspace information as JSON.

Inspect available evidence

GitHub project details can include a pinned source revision, README and license information, and attributed documentation previews. Unknowns remain labeled as unknowns.

Design for people

The interface organizes projects around what someone might want to do rather than expecting them to know programming languages or source-host terminology.

Where it could go

From finding a foundation to making something personal.

Next research areas include stronger source inspection, more reliable evidence about reuse rights, and practical planning for combinations of projects. The eventual goal is a constrained path for making and testing real changes in an isolated environment, with recovery and export.

Those capabilities are proposals, not features of the current prototype. I want to test the core experience and its limitations before promising an autonomous development platform.

Scope and contribution

An experiment, not a finished service.

Current limits: No AI-driven code modification, arbitrary-code execution, hosted user accounts, billing, or production readiness has been established. Conversational guidance is currently template-based. Workspace data is browser-local, and discovery depends on source-host APIs and their limits.

My contribution: I define the product direction, requirements, constraints, workflows, and design priorities; evaluate behavior; and guide revisions. AI tools provide substantial implementation and writing assistance. I am learning through the work, not claiming independent authorship of all its code.

The implementation repository is private while the project evolves. This page describes the current development work without exposing private source or presenting planned capabilities as operational.
